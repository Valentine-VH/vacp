# VACP 技术选型与身份体系设计

移动端固定采用 uni-app + Vue 3 + TypeScript。Web 采用 React + Vite + TypeScript，服务端首选 NestJS + Fastify，持久化首选 PostgreSQL + Drizzle。正式代码采用 pnpm workspace 和严格 TypeScript。先从单进程 API 和单数据库起步。

| 决策 | 备选 | 取舍 |
|---|---|---|
| React + Vite 管理端 | Vue 3 + Vite | 优先考虑 React 的管理台和 Agent 对话组件生态。Web 与 uni-app 共享 API 契约和权限语义。 |
| NestJS + Fastify | 直接使用 Fastify | Nest 的模块、Guard 和统一注入有利于身份与任务模块统一鉴权。原生 Fastify 更容易做短链路验证，如 PoC 所示。 |
| PostgreSQL + Drizzle | SQLite | PostgreSQL 用于正式服务的并发写入、事务与迁移。SQLite 用于本机 PoC，简化启动。 |
| 同源部署 | Web 和 API 独立发布 | 开发由 Vite 代理 API。部署可由同一入口提供 Web 静态产物和 API，移动端通过 HTTPS 使用相同 API。 |

参考 [NestJS HTTP Adapter](https://docs.nestjs.com/http/performance) 与 [uni-app 跨端原理](https://uniapp.dcloud.net.cn/frame.html)。AI 辅助效率属于工程判断，PoC 没有测量 React 与 Vue 的开发速度。

## Web 样式与对话

后台使用 Ant Design，统一表格、表单、确认弹窗、角色标签及主题变量。移动端继续使用 uni-app。

对话使用 Ant Design X。会话列表采用 Conversations，输入采用 Sender，正文采用 Bubble。工具调用、审批和产物事件放入执行过程，运行时明确提供的思考摘要单独显示。VACP 的 SSE 适配层将任务事件转成 UI 数据，对话与任务协议仍由 VACP 定义。对话组件随对话功能接入。

## Node.js 与中间件

正式 Server 和 Web 使用 Node.js 26 LTS，项目根目录的 `.nvmrc` 固定为 26.13.1。开发、CI 与 Docker 使用相同版本。Windows 的 nvm-windows 切换可能影响其他项目，开发时可通过 Node 26 的独立安装目录为当前终端设置 PATH。uni-app 先验证 H5 和目标小程序构建，再确定是否需要单独的构建版本。现有 PoC 的验证基线为 Node 24。

首版部署只依赖 PostgreSQL。用户会话、任务状态和事件持久化在 PostgreSQL。任务创建与 Outbox 记录在同一事务写入，由单实例调度器派发，Connector 用 ACK 确认接收。首版无需 Redis。独立 Worker 扩缩容、延迟与优先级调度或实测数据库轮询成为瓶颈时，再评估 Redis + BullMQ。引入队列后，PostgreSQL 仍是任务状态的权威来源。

## 知识库、会话上下文和长期记忆

| 能力 | 数据归属 | 首版方案 | 扩展条件 |
|---|---|---|---|
| 知识库 | 工作空间拥有，按用户或 Agent 授权 | PostgreSQL 保存知识库目录、外部服务引用和授权。需要检索时通过受控适配器接入现有 RAG 服务 | 需要统一管理文档时再接 S3 兼容存储。需要自建检索时再选索引和向量存储 |
| 会话上下文 | 属于原执行节点及其 Runtime 会话 | VACP 记录工作空间、发起用户、目标节点及会话引用。任务委派显式携带必要摘要和授权产物引用 | 有跨 Runtime 续接需求时，再定义可移植的摘要及引用格式 |
| 长期记忆 | 按工作空间、用户和 Agent 配置隔离 | 默认关闭，由获授权的管理员按 Agent 配置。启用后先用 Runtime 原生记忆或隔离文件，确认读写边界 | 需要跨设备恢复时引入对象存储。需要按语义检索、去重和管理记忆时，再评估独立记忆服务 |

知识检索适配器根据当前工作空间和调用身份授权，凭据由服务端持有，检索结果保留来源。委派到另一个节点时重新校验资源访问权限。VACP 的任务事件与审计记录继续存 PostgreSQL，Runtime 负责管理真正送进模型的消息、工具结果和上下文压缩。撤销成员权限后，应阻止后续检索、历史读取和记忆访问。

首个知识库集成候选为 OpenViking。已有 Vector Agent RAG 链路继续使用 Milvus，VACP 通过 Vector Agent 的服务接口调用检索；文档解析、Embedding、索引维护和结果组装归该服务。知识库配置指定检索后端，首轮分别验证，避免同一份资料重复入库。两种后端均需验证以工作空间为边界的检索授权和来源引用。

长期记忆首版采用文件，默认关闭，启用后按工作空间、用户、Agent 配置划分读写目录。由执行节点或其持久卷保管，节点迁移和跨设备同步另行设计。DSH 与 OpenCode 各自拥有会话历史和上下文处理，VACP 记录带运行时与节点标识的会话引用，跨节点委派使用显式摘要。

这些集成无需为首版增加 Redis。身份 PoC 仍以工作空间授权为验证范围。

## 身份与权限

用户是平台身份，通过工作空间成员关系获得角色。用户可加入多个工作空间，一个角色只作用于一个工作空间。平台管理权限独立于工作空间 Owner。工作空间采用 UUID，所有空间内资源带 workspace_id，服务端以登录身份与路由中的空间 ID 查询成员关系，再校验操作权限。

| 权限 | Owner | Admin | Member | Viewer |
|---|---|---|---|---|
| 查看工作空间及可读资源 | ✓ | ✓ | ✓ | ✓ |
| 创建和管理自己的任务 | ✓ | ✓ | ✓ | |
| 编辑空间资料 | ✓ | ✓ | | |
| 添加、移除和调整普通成员 | ✓ | ✓ | | |
| 授予或移除 Admin、转移所有权 | ✓ | | | |

首版角色固定。创建工作空间与建立 Owner 成员关系在同一事务中完成。转移所有权应锁定空间记录并原子更新角色，保证始终有一个 Owner。管理成员时同时检查操作者和目标角色，防止 Admin 修改 Owner 或给自己升级。未登录返回 401，无成员关系返回 404，已有成员但缺少操作权限返回 403。

Web 正式版使用同源 HttpOnly 会话 Cookie 和写操作 CSRF 防护。uni-app 采用短期访问凭据和平台适配的续期方式。两端共享请求类型、Schema 和错误结构，各自适配网络、会话存储和实时事件。插件走独立节点身份。正式版需要覆盖禁用用户、会话撤销、角色变更立即生效和审计。旧启动稿中的 Tenant 层级和 Vue Web 建议，在本设计覆盖范围内以本方案为准。

## 角色配置与菜单

首版采用工作空间级 RBAC。代码维护稳定的权限键和内置角色的权限映射。管理员可在授权范围内为成员分配角色。角色配置页可以展示只读权限矩阵，便于了解授权结果。

- 服务端根据当前用户、目标工作空间及操作权限判定访问。涉及本人资源的操作还需校验资源归属。
- Web 及 uni-app 各自声明菜单、路由与所需权限。切换工作空间时更新有效权限，菜单与按钮据此显示，直接访问页面同样检查权限。API 始终独立鉴权。
- 例如「成员」菜单对应 `members:read`，成员角色变更对应 `members:manage`，服务端另行检查操作者能管理哪些目标角色。具体权限键随对应 API 一起落地。
- 用户与成员关系存入数据库，内置角色定义随代码发布。初版采用固定菜单与固定角色映射。多个工作空间确有不同授权需求时，再支持管理员从权限目录组合自定义角色，并记录变更审计。菜单仍按有效权限显示。

验收应覆盖同一用户在不同空间看到对应菜单、只读用户直接访问写入 API 被拒绝，以及角色撤销后下一次请求立即重新判权。

工作空间所有权交接的接口和验收见 [工作空间治理阶段](workspace-governance.md)。

## PoC

位于 [poc/identity](../../poc/identity)。使用 Node 24，在该目录执行：

```powershell
pnpm install
pnpm test
pnpm build
```

用两个终端分别执行 `pnpm api` 和 `pnpm dev`，然后访问 [Web PoC](http://127.0.0.1:5173)。点击创建并登录演示账号，可查看不同角色的两个空间，并对有权限的空间改名。API 测试还验证了错误密码、匿名请求、只读写入拒绝、跨空间访问拒绝。API 绑定本机 3310，使用 SQLite 和一小时 Bearer 会话，演示重开后可创建新账号。演示账号入口仅适用于本地。

现有 PoC 使用 React 验证 Web 到 API 的最小权限切片。正式 Web 使用 React 和 Ant Design。仍需验证 uni-app H5/小程序连接、NestJS Guard、PostgreSQL 迁移、成员增删及所有权转移。
